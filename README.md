# LogLens · 网站访问日志可视化分析工具

一个基于 Flask 的本地日志分析工具。上传 Nginx / Apache `combined` 格式的访问日志，即可完成统计聚合、可视化展示与异常行为检测。所有解析与检测均在本地完成，日志文件不会上传到任何服务器。

## 一、功能特性

- **一键演示与压力测试**：内置 293 条演示日志与 10000 条压力测试日志，一键加载即可查看完整分析效果，方便现场展示。
- **统计聚合**：按小时访问趋势、Top 10 来源 IP、Top 10 请求 URL、HTTP 状态码分布、请求方法分布。
- **异常检测**：基于规则库识别 7 类风险行为，输出风险等级、命中规则与判定依据。
- **可视化**：深色 / 浅色双主题，纯前端 SVG 与 CSS 渲染的折线图、环形图、条形图，零前端依赖、无 CDN。
- **安全边界**：单文件上限 32 MB，明细表只渲染前 100 条，统计仍基于全量数据。

## 二、技术架构

| 层次 | 实现 |
| --- | --- |
| Web 框架 | Flask 3.1 |
| 日志解析 | `analyzer/parser.py`：正则提取 IP、时间、请求行、状态码、字节数、Referer、UA |
| 统计与检测 | `analyzer/stats.py`：`Counter` 聚合 + 规则检测引擎 |
| 路由控制 | `app.py`：`/` 上传分析，`/demo` 演示数据，`/stress` 万条压测数据 |
| 前端展示 | `templates/index.html`：Jinja2 模板 + 原生 JavaScript + SVG |

数据流：上传日志文件 → 逐行解析为结构化记录 → 统计聚合与异常检测 → 注入模板 → 前端图表渲染。

## 四、快速开始

```bash
# 创建并激活虚拟环境
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate

# 安装依赖
pip install -r requirements.txt

# 启动服务
python app.py
```

浏览器访问 `http://127.0.0.1:5000/`，上传 `.log` 文件，或点击「一键加载演示数据」/「万条压力测试」。

## 五、异常检测规则

| 规则 | 等级 | 判定依据 |
| --- | --- | --- |
| 敏感路径探测 | 高危 | URL 命中 `.env`、`.git`、`/admin`、`wp-login`、`phpmyadmin`、`actuator` 等敏感资源关键字 |
| 注入攻击特征 | 高危 | 带参数的请求中包含 UNION 注入、`or 1=1`、目录遍历、XSS 标签、命令执行等载荷特征（含 URL 编码变体） |
| 扫描器 UA | 中危 | User-Agent 包含 sqlmap、nikto、nmap、gobuster、curl、python-requests 等自动化工具标识 |
| 可疑请求方法 | 中危 | 出现 PUT / DELETE / TRACE / CONNECT / PATCH 等非只读方法 |
| 服务端错误 | 中危 | 响应状态码 ≥ 500 |
| 疑似目录扫描 | 中危 | 同一 IP 累计产生 ≥ 5 次 404 |
| 高频访问 | 低危 | 单一 IP 请求数 ≥ 20 且占总请求比例 ≥ 15% |

单条记录可同时命中多条规则，记录的风险等级取其中最高者；规则汇总表则按规则自身的固有等级统计。综合风险等级按「高危 > 中危 > 低危 > 安全」输出。

## 六、测试结果

### 1. 功能测试

使用 `logs/demo.log`（293 条记录）进行测试：

| 指标 | 结果 |
| --- | --- |
| 解析成功 / 失败 | 293 / 0 |
| 独立 IP / 独立 URL | 12 / 41 |
| 覆盖时段 | 08:00 — 19:00，共 12 个小时桶 |
| 检出异常 | 133 条，综合风险「高危」 |
| 规则命中 | 高频访问 89、扫描器 UA 75、目录扫描 26、敏感路径 24、服务端错误 6、注入特征 5、可疑方法 4 |

演示数据同时包含正常浏览流量与多类攻击流量，可验证统计图表的正确性、异常规则的召回情况，以及多规则叠加时的等级判定逻辑。

### 2. 万条日志压力测试

使用 `logs/stress_10000.log`（10000 条记录，1.83 MB）通过 multipart 上传走完整请求流程：

| 指标 | 结果 |
| --- | --- |
| HTTP 状态 | 200 |
| 解析 + 检测 + 页面渲染总耗时 | 0.219 秒 |
| 解析失败 | 0 |
| 独立 IP / 独立 URL | 35 / 66 |
| 检出异常 | 414 条，综合风险「高危」 |
| 响应页面大小 | 0.28 MB |

页面只渲染前 100 条明细，因此万条日志下响应体仍保持很小；统计与检测基于全量数据，不会因展示限制而失真。测试结果说明当前实现可以稳定处理万条量级的日志文件，不会出现页面卡死或崩溃。

## 七、个人总结

这个课题让我把「日志分析」从概念变成了可运行的工具。实现过程中有三个收获：一是先建立结构化解析层，再往上叠加统计与检测，模块边界清晰，后续新增规则只需改规则库；二是异常检测不能只靠单条请求判断，引入 IP 维度的聚合统计后，目录爆破和高频爬取这类"量大而单次无害"的行为才能被识别出来；三是可视化不只是把数字画成图——风险横幅、等级色标和异常明细表联动起来，演示时才能让人快速看懂结论。

压力测试也验证了"明细限量渲染"的设计价值：1 万条日志从上传到页面返回不到 0.25 秒，响应体仅 0.28 MB。目前规则的阈值以经验值为主，真实环境中还需要结合业务基线调优；后续可以考虑加入时间窗口滑动统计、IP 信誉比对与规则配置化。
